= UC-001: User Registration via Identity Provider

== Metadata

[cols="1,3"]
|===
| Primary Actor | Anonymous User with Identity Provider credentials
| Scope | Security Module - Registration Context
| Level | User Goal
| Trigger | User initiates registration through an Identity Provider
|===

== Stakeholders and Interests

*User*::
  Wants seamless registration without new passwords.
  Expects to be recognized on return visits regardless of which IdP they used.

*System Owner*::
  Needs accurate user tracking without duplication.
  Must support multiple IdPs (Auth0, Google, Microsoft) without vendor lock-in.

*Security Auditor*::
  Requires clear audit trail.
  Needs verification that identities are validated by trusted providers.

== Preconditions

* User has valid credentials with a supported Identity Provider
* Identity Provider is configured and accessible

== Postconditions

=== Success Guarantee

* New `User` aggregate created with unique surrogate ID
* `IdentityProviderUser` entity created linking User to IdP identity (`iss`, `sub`)
* Domain events published: `UserRegistered`, `IdentityLinked`

=== Minimal Guarantee

* No duplicate user records created for same IdP identity
* Failed attempts logged for audit

== Main Success Scenario

// Anchors use [#anchor] syntax which is inline and doesn't break list numbering
[#step-initiate-registration]
1. *User initiates registration via Identity Provider* +
   _User clicks "Sign up with Google/Auth0/Microsoft"_

[#step-redirect-idp]
2. *System redirects to Identity Provider for authentication* +
   _System constructs OIDC authorization request with appropriate scopes_

[#step-user-authenticates]
3. *User authenticates with Identity Provider* +
   _User enters credentials in IdP's interface (outside our system)_

[#step-idp-returns-token]
4. *Identity Provider returns OIDC token* +
   _Token contains: `iss`, `sub`, `email`, `email_verified`, `name`, `picture`_

[#step-extract-identity]
5. *System extracts identity claims* +
   _Parses `iss` (issuer URI) and `sub` (subject identifier)_

[#step-query-existing]
6. *System queries read model for existing identity* +
   _Query: Find user with matching (`issuer`, `sub`)_

[#step-check-exists]
7. *Read model returns: No user found* +
   _Identity is new, proceed with registration_

[#step-create-user-aggregate]
8. *System creates new `User` aggregate* +
   _Generates surrogate UserId, initializes user record_

[#step-create-idp-entity]
9. *System records `IdentityProviderUser` entity* +
   _Stores: `issuer`, `sub`, `email`, `emailVerified`, `name`, `picture`_

[#step-publish-events]
10. *System publishes domain events* +
    _`UserRegistered`, `IdentityLinked` events emitted_

[#step-create-session]
11. *System creates user session* +
    _Session established, user is authenticated_

[#step-redirect-app]
12. *System redirects to application* +
    _User lands on post-registration onboarding or dashboard_

== Extensions (Alternative Flows)

// Extensions reference the semantic anchors using <<anchor>> syntax
// This survives renumbering - if step 7 becomes step 8, just update the anchor location

=== At <<step-check-exists>>: User Already Exists

*Condition:* Read model finds existing user with matching (`issuer`, `sub`)

*Steps:*
. System treats this as a **login** rather than registration
. System updates cached profile information if changed
. Proceed to <<step-create-session>>

=== At <<step-idp-returns-token>>: Auth0 Account Linking Enabled

*Condition:* Auth0 has linked multiple identities to a primary account

*Steps:*
. Auth0 returns the *primary* `sub` regardless of which IdP was used
. System identifies user by primary (`iss`, `sub`)
. Audit log records the specific IdP used for traceability
. Proceed to <<step-check-exists>> (will likely find existing user)

=== At <<step-check-exists>>: Email Exists (Different IdP)

*Condition:* No match on (`iss`, `sub`), but email exists with different identity

*Steps:*
. System presents options to user:
** "Link accounts" (if they own both identities)
** "Create separate account"
** "I need help"
. If "Link accounts" selected: invoke UC-003 (Account Linking)
. If "Create separate": continue to <<step-create-user-aggregate>>
. If "Help": redirect to support flow, *ENDS*

=== At <<step-user-authenticates>>: Identity Provider Error

*Condition:* IdP returns error or is unreachable

*Steps:*
. System logs error details for troubleshooting
. Display user-friendly message: "Unable to connect to [IdP name]"
. Offer alternative registration methods if available
. *ENDS* (failed)

=== At <<step-idp-returns-token>>: Required Claims Missing

*Condition:* Token missing `iss` or `sub` claims

*Steps:*
. System logs security event (potential misconfiguration)
. Reject registration attempt
. Display error: "Incomplete identity information received"
. *ENDS* (failed)

=== At <<step-idp-returns-token>>: Email Not Verified

*Condition:* `email_verified` is false

*Steps:*
. System records this status
. May restrict certain features until email verified
. Continue to <<step-create-user-aggregate>> (user still created)

== CQRS Considerations

=== Command Side

*Command:*
[source,java]
----
record RegisterUserFromIdentityProviderCommand(
  URI issuer,
  String sub,
  String email,
  boolean emailVerified,
  String name,
  URI picture
) {}
----

*Handler:* `RegisterUserFromIdentityProviderHandler`

*Aggregate:* `User`

=== Query Side

*Query:* `FindUserByIdentityQuery(URI issuer, String sub)`

*Read Model:*
[source,java]
----
interface UserIdentityView {
  UserId userId();
  URI issuer();
  String sub();
  String email();
  boolean emailVerified();
  Instant registeredAt();
}
----

== Event Sourcing

|===
| Event | Description
| `UserRegistered` | userId, registeredAt, initialIdentity
| `IdentityLinked` | userId, issuer, sub, linkedAt
| `UserProfileUpdated` | userId, changedFields
|===

*Stream naming:* `user-{userId}`

*Snapshot policy:* Every 50 events

== Special Requirements

* `iss` stored as normalized URI (no trailing slash variations)
* `sub` stored exactly as provided (case-sensitive)
* Email is NOT an identity key (users can change emails)
* All IdP interactions logged for audit

== Technology and Data Variations

* Identity Provider: Auth0, Google, Microsoft, GitHub, any OIDC provider
* Token format: JWT or opaque (via userinfo endpoint)
* Profile picture: URL provided or fetched separately
