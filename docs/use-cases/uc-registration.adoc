= UC-001: User Registration via Identity Provider

== Metadata

[cols="1,3"]
|===
| Primary Actor | Anonymous <<Person>> with Identity Provider credentials
| Scope | Security Module - Registration Context
| Level | User Goal
| Trigger | User initiates registration through an Identity Provider
|===

== Stakeholders and Interests

*<<Person>>*::
  Wants seamless registration without creating new passwords.
  Expects to be recognized on return visits regardless of which IdP they used.

*System Owner*::
  Needs accurate user tracking without duplication.
  Must support multiple IdPs without vendor lock-in.

*Security Auditor*::
  Requires clear audit trail.
  Needs verification that identities are validated by trusted providers.

== Preconditions

* <<Person>> has valid credentials with a supported Identity Provider
* Identity Provider is configured and accessible

== Postconditions

=== Success Guarantee

* <<User>> created with unique identifier
* <<IdentityProviderUser>> created linking <<User>> to external identity
* Domain events published for user registration and identity linkage
* Personal <<Account>> created (see <<account-creation,open issue>>)

=== Minimal Guarantee

* No duplicate <<User,Users>> created for same identity
* Failed attempts logged for audit

== Main Success Scenario

. [[step-initiate,User initiates registration via Identity Provider]] *User initiates registration via Identity Provider* +
  _User clicks "Sign up with..." button for chosen provider_

. [[step-authenticate,System authenticates user through Identity Provider]] *System authenticates user through Identity Provider* +
  _User completes login at provider; System receives identity token containing
  issuer, subject identifier, email, and profile information_

. [[step-validate,System validates identity is new]] *System validates identity is new* +
  _System queries whether identity (issuer + subject) already exists_

. [[step-create,System creates User and links Identity Provider identity]] *System creates User and links Identity Provider identity* +
  _New <<User>> created; <<IdentityProviderUser>> record created with issuer, subject, and profile information from provider_

. [[step-create-account,System creates personal Account]] *System creates personal Account* +
  _New <<Account>> created for the <<User>>; <<User>> added as owner (see open issue)_

. [[step-publish,System publishes registration events]] *System publishes registration events* +
  _User registered and identity linked events emitted for downstream processing_

. [[step-complete,System signs in user and opens application]] *System signs in user and opens application* +
  _User authenticated and redirected to application_

== Extensions (Alternative Flows)

=== During <<step-validate>>: User Already Exists

*Condition:* Identity (issuer + subject) found in system

*Steps:*
. System treats this as sign-in rather than registration
. System updates cached profile information if changed
. Resume at <<step-complete>>

=== During <<step-authenticate>>: Auth0 Account Linking Enabled

*Condition:* Auth0 has linked multiple identities to a primary account

*Steps:*
. Auth0 returns the primary subject identifier regardless of which IdP was used
. System identifies user by the primary identity
. Audit log records the specific IdP used for traceability
. Continue with <<step-validate>> (typically finds existing user)

=== During <<step-validate>>: Email Exists with Different Identity

*Condition:* Identity not found, but email address exists with different identity

*Steps:*
. System presents options to user:
** "Link these accounts" (if they own both identities)
** "Create separate account"
** "I need help"
. If "Link accounts" selected: invoke UC-003 (Account Linking)
. If "Create separate": continue with <<step-create-account>>
. If "Help": redirect to support flow, *ENDS*

=== During <<step-authenticate>>: Identity Provider Unavailable

*Condition:* Identity Provider returns error or is unreachable

*Steps:*
. System logs error details for troubleshooting
. Display user-friendly message: "Unable to connect to [provider name]"
. Offer alternative registration methods if available
. *ENDS* (failed)

=== During <<step-authenticate>>: Required Claims Missing

*Condition:* Identity token missing required claims (issuer or subject)

*Steps:*
. System logs security event
. Reject registration attempt
. Display error: "Incomplete identity information received"
. *ENDS* (failed)

=== During <<step-authenticate>>: Email Not Verified

*Condition:* Email verification status from provider is false

*Steps:*
. System records unverified email status
. May restrict certain features until email verified
. Continue with <<step-create>> (<<User>> still created)

== Technology and Data Variations

=== Identity Providers Supported
* Auth0 (OIDC)
* Google (OIDC)
* Microsoft/Azure AD (OIDC)
* GitHub (OIDC)
* Any OIDC-compliant provider

=== Token Formats
* JWT (JSON Web Token)
* Opaque token (via userinfo endpoint)

=== Profile Information
* Email address (not used as identity key - users can change emails)
* Email verification status
* Display name
* Profile picture URL

== Special Requirements

* Issuer (provider identifier) stored as normalized URI
* Subject identifier stored exactly as provided (case-sensitive, immutable)
* Email addresses are not identity keys
* All provider interactions logged for security audit
* Idempotent registration (same identity cannot create duplicate accounts)

== Frequency of Occurrence

Expected to be primary user acquisition path.
Estimated: 100-1000 registrations per day initially.

== Design Decisions

=== Email Uniqueness Constraint

*Problem:*
In event sourcing, aggregates are identified by their aggregate ID (UUID in this case).
However, we need to enforce that email addresses are globally unique to prevent duplicate user registrations.
Unlike an SQL database, we cannot simply add a `UNIQUE` constraint on a column.

*Options Considered:*

[cols="1,3,3"]
|===
| Option | Description | Trade-offs

| **Email as Aggregate ID**
| Use the email string as the `User` aggregate identifier instead of a UUID.
| *Pros:* Simplest code; Axon enforces uniqueness automatically via ID collision.
*Cons:* Email changes become operationally complex (requires rewriting event streams);
email (PII) appears in all stream IDs and logs; external references must use email as FK.

| **Actor Model (Separate Aggregate)**
| Create an `EmailClaim` aggregate with email as its ID;
chain creation to `User` aggregate creation.
| *Pros:* Uses Axon's built-in locking; no race conditions.
*Cons:* More boilerplate (new aggregate, events, command handlers);
complex orchestration between aggregates.

| **EventStore Tag Query (Chosen)**
| Tag `UserCreated` events with email;
query EventStore by tag before creating user.
| *Pros:* Minimal code; keeps UUID as stable ID; email can change in future.
*Cons:* Requires understanding of Axon 5 tags;
slight risk of race condition (mitigated by `AppendCondition`).
|===

*Decision:*
Use **EventStore Tag Query** with idempotent behavior.
When `RegisterNewUser` is received, query EventStore for existing events tagged with the email.
If found, return success with no new events (idempotent).
If not found, append `UserCreated` event.

*Rationale:*
Email changes should be "extremely rare but possible" - using mutable data as aggregate ID is an anti-pattern.
The UUID provides a stable identifier for external references and future email changes.
The tag query provides the minimal code solution while maintaining flexibility.

=== Dynamic Consistency Boundary (DCB) and the User Aggregate

*Context:*
Axon Framework 5 introduces Dynamic Consistency Boundary (DCB), which shifts from the traditional aggregate-centric model.
In DCB, events are tagged with multiple identifiers (not just aggregate ID), allowing queries by any business key.

*Why the User aggregate isn't loaded in the first step:*

Registration has two conceptual steps:
1. **Create User** (current step) - emits `UserCreated` event 2. **Link Identity Provider** (next step) - loads `User` aggregate, calls `linkIdentityProvider()`

In the first step, we don't load the `User` aggregate because:
- The user doesn't exist yet (we're checking if email is available) - We don't know the aggregate ID yet (it's generated as a new UUID) - We only have the email (a tag, not the aggregate identifier) - The check is simple existence - no state transitions needed

DCB allows us to query by email tag directly without needing an aggregate.

*When the User aggregate IS used:*

The `User` aggregate is used for the second step (linking the IdP) and any operation that requires:
- Loading existing state by aggregate ID - State evolution (calling methods that emit events) - Instance-level business rules (e.g., "can only link if email verified")

*Example of aggregate usage:*

```
LinkIdentityProvider command → Load User by ID →
user.linkIdentityProvider(issuer, subject) → Append IdentityProviderLinked event
```

*Summary:*
The registration command handler uses DCB tags for existence checking (step 1).
The `User` aggregate is created by the `UserCreated` event and will be used in subsequent steps.
DCB enables querying by business keys (email) while aggregates remain the primary model for state transitions.
